# wgctl

Manages the WireGuard peers on `orion`. One Python script, no dependencies
beyond `wireguard-tools` and (optionally) `qrencode`. Runs in place from a
checkout; nothing is installed.

Replaces `mkconfig.sh`. Migrating from it: **[MIGRATION.md](MIGRATION.md)**.

## Model

`peers.json` is the source of truth. The running interface and
`/etc/wireguard/wg0.conf` are *derived* from it:

```
./wgctl add / rm / rotate / disable     edit the registry
./wgctl apply                           reconcile the server with the registry
```

`apply` is idempotent and does both directions — it loads new peers and
removes deleted ones in one step, via `wg syncconf`, so established sessions
for unchanged peers are not interrupted. Because the server is always
reconciled rather than incrementally patched, `./wgctl list` is the truth and
the interface cannot silently drift out of step.

Two rules make that hold, both enforced by `./wgctl check`:

- `SaveConfig` must stay **off**. With it on, `wg-quick down` overwrites
  `wg0.conf` from live kernel state, destroying the peer-name comments and any
  hand edit.
- Nothing else edits `wg0.conf`. Forwarding and NAT belong to ufw, not
  `PostUp` rules — see MIGRATION.md for why.

## Where things live

State stays in the checkout, under `state/`:

| Path                    | Mode | Contents                                             |
|-------------------------|------|------------------------------------------------------|
| `state/peers.json`      | 644  | public keys, addresses, profiles                     |
| `state/secrets/<name>/` | 700  | client private key and preshared key                 |
| `state/out/<name>/`     | 700  | rendered client configs (these contain private keys) |

`state/` is created mode 0700 owned by root, so reading it needs `sudo`. It is
gitignored, and so is your `wgctl.conf`.

Two files are the exception and live in `/etc/wireguard/`, because `wg-quick`
requires them there:

- `privatekey` — the server's own identity, not per-peer state
- `wg0.conf` — generated by `./wgctl apply`; `wg-quick@wg0` reads that exact path

Relative paths in `wgctl.conf` resolve against the config file's own directory,
so moving or re-cloning the checkout moves everything with it.

## Setup

```bash
sudo apt install wireguard qrencode
cp wgctl.conf.example wgctl.conf
vim wgctl.conf                   # endpoint, subnets, profiles
sudo ./wgctl check
```

Root is needed to read the server key, write `/etc/wireguard/wg0.conf`, and
talk to the interface. `--config` and `$WGCTL_CONFIG` override the lookup,
which otherwise checks beside the script, then the working directory, then
`/etc/wgctl/wgctl.conf`.

## First-time server setup

Skip to MIGRATION.md if the server already runs WireGuard.

**1. Server key.** The public key is derived from it on demand and never
stored separately.

```bash
sudo sh -c 'umask 077 && wg genkey > /etc/wireguard/privatekey'
```

**2. Forwarding.** In `/etc/sysctl.conf`:

```
net.ipv4.ip_forward=1
net.ipv6.conf.all.forwarding=1
```

Then `sudo sysctl -p`.

**3. Firewall.** ufw owns NAT and forwarding. Add this `*nat` block at the top
of `/etc/ufw/before.rules`, above the existing `*filter` line, matching
`ipv4_subnet` and `wan_interface` from your config:

```
*nat
:POSTROUTING ACCEPT [0:0]
-A POSTROUTING -s 10.8.0.0/24 -o eth0 -j MASQUERADE
COMMIT
```

Nothing goes in `before6.rules` — a routed IPv6 prefix needs no NAT.

```bash
sudo ufw allow 51820/udp comment wireguard
sudo ufw route allow in on wg0 out on eth0   # clients -> internet
sudo ufw route allow in on wg0 out on wg0    # peer to peer, incl. in-VPN DNS
sudo ufw reload
```

There is deliberately **no** rule allowing `eth0 -> wg0`. Replies to
client-initiated connections are already accepted by ufw's
`RELATED,ESTABLISHED` rule, so unsolicited inbound traffic hits the `DROP`
policy. This is what stops clients' globally routable IPv6 addresses from
being reachable from the internet.

**4. IPv6.** `ipv6_subnet` must be a prefix *routed* to this host, not the
on-link `/64` the provider assigns to `eth0`. On Linode: the instance's
Network tab, "Add an IPv6 range". `wgctl` puts it on `wg0` for you; it does
not belong on `eth0`.

Client IPv6 addresses are derived from their IPv4 address so the two read the
same: `10.8.0.22` becomes `…:0315::22`.

**5. Start.**

```bash
sudo ./wgctl apply                        # writes /etc/wireguard/wg0.conf
sudo systemctl enable --now wg-quick@wg0
sudo ./wgctl check
```

## Daily use

Run from the checkout:

```bash
sudo ./wgctl add hugo-laptop --apply      # allocate, key, render, load
sudo ./wgctl list                         # registry + live handshakes
sudo ./wgctl qr hugo-laptop full-vpndns   # scan from the phone app
sudo ./wgctl disable matt --apply         # revoke, reversibly
sudo ./wgctl rm matt --apply              # revoke permanently
sudo ./wgctl rotate drake --apply         # new keys, same address
sudo ./wgctl apply --dry-run              # show pending changes, touch nothing
```

Configs land in `state/out/<name>/<profile>.conf`. `sudo ./wgctl show <name>
[profile]` prints one to stdout instead. The file is named for the profile
alone because importers (NetworkManager/KDE, `wg-quick`) turn the file name
into the interface name, which the kernel caps at 15 characters; the peer's
name is the directory, and is repeated in a comment inside the file. Rendering
also deletes configs in that directory that the peer no longer has a profile
for.

`--apply` is a convenience; without it the registry changes and the server is
untouched until you run `./wgctl apply`.

Run `./wgctl <command> --help` for options. `sudo ./wgctl check` validates the
config, registry, permissions, and firewall, and exits non-zero on real errors.

### Adding or changing a peer's profiles

```bash
sudo ./wgctl render drake --profile full-vpndns --profile split-nodns
```

### Reissuing configs after a config change

Changing the endpoint, DNS, or IPv6 prefix does not require new keys:

```bash
sudo ./wgctl render --all    # rewrite every client config from stored keys
```

Then redistribute. `rotate` is the different operation — it issues **new
keys**, invalidating the old config. Use it when a device is lost or a config
leaked.

### Preshared keys

New peers get one automatically (`--no-psk` to skip). It is the documented
hedge against a future attacker recording traffic now and breaking the key
exchange later. Adding one to an existing peer means `./wgctl rotate` — the
tunnel breaks until the client gets the new config, so do it when you can
reach the device.

## Profiles

A profile pairs routing with DNS. Defined in `wgctl.conf`; each peer gets a
config file per profile, all sharing one keypair. Only one can be active at a
time on a device, so switching is a two-tap operation in the client app with
no rekeying.

| Profile        | Tunnels          | Resolver                         |
|----------------|------------------|----------------------------------|
| `full-vpndns`  | everything       | in-VPN DNS                       |
| `full-pubdns`  | everything       | `1.1.1.1`                        |
| `split-vpndns` | VPN subnets only | in-VPN DNS                       |
| `split-nodns`  | VPN subnets only | whatever the local network gives |

The `*-pubdns` and `*-nodns` variants exist because a `*-vpndns` config has no
resolver at all when the in-VPN one stops answering, which presents as "the
internet is broken". Internal names still resolve on the fallback profiles
because their records live in a public zone.

Keep profile names to 15 characters and to `A-Z a-z 0-9 _ = + . -`, for the
import reason above; `./wgctl check` warns when one is too long to import.

`wgctl` refuses to start if a profile sets a DNS address its own `AllowedIPs`
do not route — the silently-wrong combination where queries look tunnelled but
leave over the local link. Search domains are not supported; use FQDNs.

## Troubleshooting

**Handshakes succeed but no traffic passes.** Forwarding. `./wgctl check`
covers the usual causes; `sudo ufw show added` should list both `route allow`
rules. If they are missing, step 3 above was lost.

**No DNS on a `*-vpndns` profile.** The in-VPN resolver is not answering.
Switch the device to `full-pubdns`, then from a connected client check the
resolver itself: `dig @10.8.0.1 immich.hugo-klepsch.tech`.

**SSH works, HTTPS hangs.** MTU. Set `mtu = 1380` in `wgctl.conf`,
`./wgctl render --all`, redistribute.

**A peer on the interface is not in the registry.** `./wgctl list` warns about
these; `./wgctl apply` removes them. If it should exist, add it deliberately.

**IPv6 specifically is broken.** Check `ip -6 addr show wg0` has an address
from `ipv6_subnet`, that the prefix is *routed* to this host and not just
on-link, and that `net.ipv6.conf.all.forwarding` is 1. `eth0`'s own IPv6
address is managed by systemd-networkd in userspace, which is why
`net.ipv6.conf.eth0.accept_ra` reads 0 — that is expected, not a fault.
Confirm with `networkctl status eth0`.

**`wg` shows a peer but `wgctl` disagrees.** `./wgctl apply` reconciles; the
registry wins.
